# AGENTS.MD — правила работы агента в проекте PortalProstoev

Проект: портал учёта простоев по вине ИТ-компании для промышленного сектора.
Полное описание проекта — в `project.md`.

## Главный принцип: понятность для владельца проекта
Владелец проекта — специалист, **почти не программирует** (сильная сторона — SQL и базы данных).
Поэтому код должен быть понятным и сопровождаемым им, а не «умным».

Обязательно:
- **Каждое изменение сопровождать объяснением простыми словами** — что сделано и зачем.
- **Модули держать маленькими** — один файл = одна ответственность.
- **Комментировать неочевидную логику на русском** прямо в коде.
- **Документировать рядом с кодом** — файл в `docs/` на каждый модуль (что делает, какие данные, какие правила).
- **Не тащить лишние технологии** — если можно решить средствами Django, решать ими.
- **Идти маленькими шагами**: сначала показать и объяснить один модуль, дождаться вопросов, потом следующий.

## Обязательные правила документации
- **README.md** обновлять при изменении: запуска, переменных окружения, состава модулей, миграций, тестов.
- **AGENTS.MD** обновлять при изменении: правил агента, стека, соглашений о коде, структуры репозитория.
- Обновление документации — часть Definition of Done. Документацию коммитить вместе с кодом, а не отдельно.

## Ключевые технические решения
- **Стек:** Python 3.12+ + Django 6.x, Django Templates + HTMX, Chart.js. Без React и сборки фронтенда.
- **App DB:** PostgreSQL + Django ORM.
- **Аутентификация:** `django-auth-adfs` (prod), dev-вход (локально). Маппинг групп AD → роли.
- **Источник простоев:** Oracle DB (второй уровень), read-only через `python-oracledb`.
- **ITIL-тикеты:** OMNITRACKER (связь many-to-many с инцидентами портала).
- **Тесты:** pytest + pytest-django.

## Среды разработки и прода (важно)
- **Сейчас:** разработка на домашнем Windows-ПК в WSL без доступа к домену, Oracle DB и OMNITRACKER. Код обязан собираться и работать без этих ресурсов.
- **Позже:** перенос на Oracle Linux-сервер в корпоративной доменной сети, где все системы доступны.
- **Правило:** любую внешнюю интеграцию реализовывать за адаптером с реализациями `mock` и `live`; режим — через `.env` (`INTEGRATION_MODE`, `AUTH_MODE`).
- Не добавлять жёстких зависимостей от корпоративных сервисов на старте; при недоступности — работать в mock-режиме, не падать.
- Секреты и строки подключения к прод-системам в репозиторий не коммитить.

## Правила кода
- Секреты только в `.env` / `.env.example`.
- Деньги и длительности считаются только на сервере (в `services.py`), не в шаблонах.
- Бизнес-логику держать в `services.py`, а не во `views.py` и не в моделях «наугад».
- Импорт из Oracle идемпотентен (без дублей).
- Все важные изменения данных писать в журнал аудита.
- Каждая функция/вьюха — с docstring по-русски: что делает и какие данные трогает.
