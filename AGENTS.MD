# AGENTS.MD — правила работы агента в проекте PortalProstoev

Проект: портал учёта простоев по вине ИТ-компании для промышленного сектора.
Полное описание проекта — в `project.md`.

## Главный принцип: понятность для владельца проекта
Владелец проекта — специалист, **почти не программирует** и не является разработчиком или
администратором БД. Поэтому объяснять нужно максимально простыми словами, без технического жаргона.
Поэтому код должен быть понятным и сопровождаемым им, а не «умным».

Обязательно:
- **Каждое изменение сопровождать объяснением простыми словами** — что сделано и зачем.
- **Модули держать маленькими** — один файл = одна ответственность.
- **Комментировать неочевидную логику на русском** прямо в коде.
- **Документировать рядом с кодом** — файл в `docs/` на каждый модуль (что делает, какие данные, какие правила). Оглавление всей документации — `docs/README.md`.
- **Не тащить лишние технологии** — если можно решить средствами Django, решать ими.
- **Идти маленькими шагами**: сначала показать и объяснить один модуль, дождаться вопросов, потом следующий.

## Обязательные правила документации
- **README.md** обновлять при изменении: запуска, переменных окружения, состава модулей, миграций, тестов.
- **AGENTS.MD** обновлять при изменении: правил агента, стека, соглашений о коде, структуры репозитория.
- Обновление документации — часть Definition of Done. Документацию коммитить вместе с кодом, а не отдельно.

## Ключевые технические решения
- **Стек:** Python 3.12+ + Django 6.x, Django Templates + немного JavaScript, Chart.js. Без React и сборки фронтенда.
- **App DB:** PostgreSQL + Django ORM.
- **Аутентификация:** корпоративный вход (SSO) через `django-auth-adfs` (prod), dev-вход (локально). Маппинг групп AD → роли.
- **Источник простоев:** внешняя корпоративная БД с простоями, read-only. Портал **не собирает** простои сам — читает их из БД и **фильтрует** по вине ИТ.
- **ITIL-тикеты:** система тикетов (связь many-to-many с инцидентами портала).
- **Тесты:** встроенный Django-раннер (`manage.py test`); тесты — в `apps/<модуль>/tests.py`. Автопрогон при каждом push — GitHub Actions (`.github/workflows/tests.yml`).
- **Интеграции — только за адаптерами** `mock`/`live` (`apps/integrations/*`); выбор режима — через `.env` (`INTEGRATION_MODE`). Доменная логика не знает про режим. Драйвер внешней БД и `requests` подключаются лениво и нужны только в live-режиме (`requirements-live.txt`).
- **Отчёты ничего не считают сами** (`apps/reports/*`): формулы (потери, доступность, MTTR/MTBF, штрафы) живут только в `apps/sla/services.py`, отчёты их переиспользуют. Так цифры на дашборде, в отчёте и на `/sla/` всегда совпадают.
- **Фронтенд без интернета:** библиотека графиков Chart.js лежит локально (`static/vendor/`), а не тянется с CDN. Страница должна работать и без графиков (цифры дублируем в таблицах).
- **Уведомления (`apps/notifications/`) — только email, канал за абстракцией** (`channels.py`): правила и получатели в БД, защита от повторов через `dedup_key` в журнале. В dev письма печатаются в консоль, на проде — SMTP. Запуск по расписанию — команды `check_escalations` и `send_digest`.
- **Демо-стенд одной командой:** `manage.py seed_demo` наполняет портал по порядку (справочники → простои → SLA → уведомления → пользователи) и безопасен для повторного запуска. Материалы приёмки — `docs/приёмка.md`, рабочее КЗ — `docs/КЗ.md`.
- **Вход и роли (`apps/accounts/`) за флагом `AUTH_MODE`:** в dev — обычная страница входа Django, на проде — корпоративный вход (SSO) (`django-auth-adfs`, настройки в `config/settings/adfs.py`, подключаются только при `AUTH_MODE=adfs`). Роль — это группа Django; страницы закрываются `@login_required`, доступ по ролям — `role_required()`. Пакет `django-auth-adfs` нужен только на проде (`requirements-live.txt`), на dev он не импортируется.

## Среды разработки и прода (важно)
- **Сейчас:** разработка на домашнем Windows-ПК в WSL без доступа к домену, внешней БД и системе тикетов. Код обязан собираться и работать без этих ресурсов.
- **Позже:** перенос на Oracle Linux-сервер в корпоративной доменной сети, где все системы доступны.
- **Правило:** любую внешнюю интеграцию реализовывать за адаптером с реализациями `mock` и `live`; режим — через `.env` (`INTEGRATION_MODE`, `AUTH_MODE`).
- Не добавлять жёстких зависимостей от корпоративных сервисов на старте; при недоступности — работать в mock-режиме, не падать.
- Секреты и строки подключения к прод-системам в репозиторий не коммитить.

## Развёртывание на прод
- Готовые файлы развёртывания — в `deploy/`: служба systemd для gunicorn, конфиг nginx, скрипт
  резервного копирования БД, пример расписания cron. Пошаговая инструкция — `docs/внедрение.md`.
- **Цель:** перенос на прод = скопировать код, заполнить `.env` и запустить. Правок кода на сервере быть не должно.
- HTTPS завершается на nginx; до приложения доходит обычный http. Django узнаёт об этом через
  `SECURE_PROXY_SSL_HEADER` (`config/settings/prod.py`) — без этого получается бесконечный редирект.
- Маршруты SSO (`oauth2/`) подключаются в `config/urls.py` **только при `AUTH_MODE=adfs`**: на dev
  пакет `django-auth-adfs` не установлен, и безусловное подключение сломало бы запуск.
- Статику на проде отдаёт nginx из `STATIC_ROOT` (после `collectstatic`); само приложение статику не раздаёт.
- Прод-зависимости — `requirements-live.txt` (добавляет драйвер источника и `django-auth-adfs`).

## Правила кода
- Секреты только в `.env` / `.env.example`.
- Деньги и длительности считаются только на сервере (в `services.py`), не в шаблонах.
- Бизнес-логику держать в `services.py`, а не во `views.py` и не в моделях «наугад».
- Импорт простоев идемпотентен (без дублей).
- Все важные изменения данных писать в журнал аудита.
- Каждая функция/вьюха — с docstring по-русски: что делает и какие данные трогает.

## Соглашения по данным
- **Справочники опознаются по названию, а не по коду.** В источнике кодов нет —
  есть только названия (например, «Цех-4»). Поэтому уникальность: название внутри родителя
  (цех уникален в предприятии, участок — в цехе, агрегат — в участке). Поле «код» необязательное.
- **Иерархия:** Предприятие → Цех → Участок → Агрегат. Верхние уровни не дублируются в нижних
  таблицах (у простоя хранится цех, предприятие вычисляется через него).
- **Вычисляемые поля пересчитываются в `save()`.** Пример: длительность простоя хранится в БД,
  но всегда пересчитывается из начала/конца при сохранении.
- **Аудит — через `services.save_with_audit()`**, а не разными способами в разных местах.
- **Без двойного счёта:** событие, входящее в кейс, отдельно не считается. Длительность кейса —
  объединение интервалов входящих событий (`services.union_duration_min`).
- **Все деньги и KPI считаются в `apps/sla/services.py`** по формуле
  `часы × ставка_участка`. Ставки версионируются по датам — берётся ставка,
  действовавшая на дату простоя. Потери не хранятся, а считаются на лету (ставки меняются).
- **В SLA/потери входят только простые вины ИТ** со статусом «Подтверждён» или «Закрыт».
  Кейс считается одним инцидентом (по своей длительности), одиночный простой — тоже один инцидент.
