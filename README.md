# PortalProstoev

Портал учёта простоев по вине ИТ-компании для промышленного сектора: фильтрация простоев
из БД с простоями, классификация вины ИТ, конструктор объединённых простоев, расчёт потерь и SLA,
дашборды и KPI, управление инцидентами и RCA, отчётность для руководства и заказчика.

## Технологический стек
- **Язык + фреймворк:** Python 3.12+ + Django 6.x
- **Интерфейс:** Django Templates + HTMX, графики Chart.js (без React)
- **Админка/CRUD:** Django Admin
- **БД приложения:** PostgreSQL + Django ORM
- **Источник простоев:** база с простоями (внешняя корпоративная БД) — read-only; портал читает из неё простои и **фильтрует** по вине ИТ, сам их не собирает
- **ITIL-тикеты:** система тикетов
- **Аутентификация:** корпоративный вход (SSO) через `django-auth-adfs`, маппинг групп AD → роли
- **Тесты:** встроенный Django-раннер (`manage.py test`) + автопрогон в GitHub Actions
- **Инфра:** Docker + docker-compose

Стек выбран сознательно простым: приоритет — понятность и сопровождаемость, а не «модность».

## Среды и развёртывание
| | Разработка (сейчас) | Прод (позже) |
|---|---|---|
| Хост | Windows + WSL2 (Ubuntu) | Oracle Linux-сервер в корпоративной доменной сети |
| База с простоями | недоступна | доступна (read-only) |
| Система тикетов | недоступна | доступна через API |
| Корпоративный вход (SSO) / домен | недоступен | доступен (вход сотрудников) |

**Ключевое требование:** проект разрабатывается и запускается локально в WSL **без доступа** к
корпоративным ресурсам. Все внешние интеграции работают в **mock-режиме**, включаемом через `.env`.
При переносе на прод те же адаптеры переключаются на реальные системы без изменения логики и шаблонов.

Флаги окружения:
```
INTEGRATION_MODE=mock        # mock | live   (БД с простоями, система тикетов)
AUTH_MODE=dev                # dev  | adfs   (вход: dev-логин | корпоративный SSO)
DATABASE_URL=...             # локальный PostgreSQL (порт 5433)
POSTGRES_*                   # параметры БД, см. .env.example
```

## Быстрый старт (разработка в WSL)
```bash
# 1. Настройки
cp .env.example .env

# 2. Зависимости
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt

# 3. Локальный PostgreSQL (порт 5433 — 5432 занят другими проектами)
docker compose up -d

# 4. Структура БД
./.venv/bin/python manage.py migrate

# 5. Администратор и данные (один раз)
./.venv/bin/python manage.py createsuperuser
./.venv/bin/python manage.py seed_catalog       # справочники
./.venv/bin/python manage.py seed_downtimes     # демо-простои
./.venv/bin/python manage.py seed_sla           # демо-договоры SLA
./.venv/bin/python manage.py seed_notifications # демо-правила уведомлений
./.venv/bin/python manage.py seed_users         # демо-пользователи по ролям
# либо всё сразу: ./.venv/bin/python manage.py seed_demo
# (необязательно) импорт простоев из БД с простоями в mock-режиме
./.venv/bin/python manage.py import_saarc

# 6. Запуск
./.venv/bin/python manage.py runserver
```
Открыть: http://127.0.0.1:8000/ — портал попросит **войти** (страница входа).
В разработке вход обычный, логин/пароль. Админ из шага 5, демо-пользователи — из `seed_users`
(пароль `DevPortal2026!`): `operator`, `specialist`, `it_manager`, `management`.
Дашборд — http://127.0.0.1:8000/, отчёт по потерям — /sla/, SLA-отчёт — /reports/sla/,
журнал уведомлений — /notifications/, админка — /admin/.
Подробно — в [`docs/каркас.md`](docs/каркас.md) и [`docs/модуль-accounts.md`](docs/модуль-accounts.md).

## Тесты
```bash
./.venv/bin/python manage.py test              # все тесты
./.venv/bin/python manage.py test apps.sla     # тесты одного модуля
```
У каждого модуля свой файл `apps/<модуль>/tests.py`. Тесты запускаются автоматически при
каждом push в GitHub (файл `.github/workflows/tests.yml`).

## Развёртывание на прод
Перенос на боевой сервер (Oracle Linux, доменная сеть) описан пошагово простыми словами —
[`docs/внедрение.md`](docs/внедрение.md). Готовые файлы развёртывания — в папке [`deploy/`](deploy/):
служба systemd для gunicorn, конфиг nginx (HTTPS + статика), скрипт резервного копирования
и пример расписания cron. На проде в `.env` ставятся `INTEGRATION_MODE=live` и `AUTH_MODE=adfs` —
код при этом не меняется, только настройки.

## Принципы разработки
- Мок-режим обязателен: проект собирается и работает без доступа в домен.
- Секреты только в `.env` / `.env.example`.
- Деньги и длительности считаются только на сервере.
- Импорт простоев идемпотентен (без дублей).
- Бизнес-логика — в `services.py`, не в шаблонах.
