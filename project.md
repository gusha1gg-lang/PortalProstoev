# PortalProstoev — портал учёта простоев по вине ИТ-компании

Портал для промышленного предприятия: учёт простоев, вызванных сбоями ИТ-инфраструктуры, расчёт потерь и SLA, дашборды, управление инцидентами и RCA.

## Технологический стек
- **Язык + фреймворк:** Python 3.12+ + Django 6.x (в dev фактически Python 3.14, Django 6.1). Один язык — проще читать и сопровождать.
- **Интерфейс:** Django Templates + HTMX (без React и сборки фронтенда). Графики — Chart.js.
- **Админка и CRUD:** Django Admin (справочники, простои, ставки — «из коробки»).
- **App DB:** PostgreSQL + Django ORM.
- **Источник данных о простоях:** Oracle DB (данные приходят со второго уровня), доступ read-only через `python-oracledb`.
- **Аутентификация:** ADFS через пакет `django-auth-adfs` (SAML/OIDC), маппинг групп AD → роли.
- **ITIL-тикеты:** OMNITRACKER — отдельный адаптер, связь many-to-many с инцидентами портала.
- **Фоновые задачи/напоминания:** Django Management Commands + cron для эскалаций и уведомлений.
- **Тесты:** pytest + pytest-django.
- **Инфра:** Docker + docker-compose, переменные окружения через `.env`.

> Примечание: стек сознательно выбран простым. Приоритет — понятность и сопровождаемость, а не «модность».

## Среды и развёртывание
**Разработка (сейчас):** домашний ПК на Windows + WSL2 (Ubuntu). Нет доступа к корпоративному домену, Oracle DB и OMNITRACKER. Проект обязан собираться, запускаться и полноценно демонстрировать сценарии в этом окружении.

**Прод (позже):** Oracle Linux-сервер в корпоративной доменной сети. Доступны реальные Oracle DB, OMNITRACKER и ADFS. Перенос выполняется без изменения доменной логики и шаблонов — только сменой флагов окружения.

Обязательные требования к переносимости:
- Все внешние системы — за адаптерами с двумя реализациями: `mock` (dev) и `live` (prod).
- Режим выбирается через `.env`: `INTEGRATION_MODE=mock|live`, `AUTH_MODE=dev|adfs`.
- В `mock`-режиме: фикстуры/seed-данные (категории вины ИТ, ставки потерь, тестовые простои), имитация ответов OMNITRACKER, dev-вход вместо ADFS.
- Приложение не должно падать при старте, если корпоративные ресурсы недоступны.
- Реальные секреты — только в `.env` на проде, в репозиторий не попадают.

## Интеграции и источники данных
1. **Oracle DB (приоритетный источник)** — периодический идемпотентный синк простоев со второго уровня, дедупликация по внешнему ID + временному окну.
2. **Ручной ввод оператором** — форма регистрации события.
3. **ITIL-тикеты: OMNITRACKER** — интеграция через API/сервисы; инцидент портала ↔ тикет, связь many-to-many.
4. Все интеграции — за интерфейсами в `apps/integrations/*` (`mock` и `live`), доменная логика их не знает.

## План внедрения, гейты и КЗ
Порядок: **прототип → КЗ → внедрение.** Подробный план — в `docs/план.md` (после переноса) и в рабочем журнале проекта.

Ключевые контрольные точки:
- **Гейт A (после модели данных и ролей):** проработать черновик КЗ, чтобы требования безопасности вошли в архитектуру, а не догоняли её.
- **Гейт B (после приёмки mock-версии):** оформить рабочее КЗ на утверждение — условие перехода к внедрению и проду.

**КЗ (классификационное заключение)** — документ, которым проект официально принимается в компанию: обоснование, дальнейшее внедрение и затраты на работы. Готовит автор проекта, утверждает служба безопасности. Содержит: назначение и проблему, область применения и обрабатываемые данные, готовый прототип, класс системы и требования безопасности (доступ, логирование, хранение, резервное копирование), перечень интеграций (Oracle, OMNITRACKER, ADFS), оценку затрат, ожидаемый эффект, этапы внедрения и ответственных, список согласующих.

## Ключевые функции
- Регистрация и учёт простоев (ручной ввод + импорт из Oracle).
- Классификация вины ИТ (категории и подкатегории, признак «вина ИТ-компании»).
- Конструктор простоя — объединение нескольких событий в один кейс с агрегацией без двойного счёта.
- Расчёт потерь (₽, тонны, часы) и штрафов по SLA.
- Дашборды и KPI: доступность, MTTR, MTBF, доля простоев по вине ИТ, топ причин.
- Инциденты и RCA (5 Whys / Fishbone).
- Отчётность: для руководства предприятия и SLA-отчётность для заказчика.
- Уведомления и эскалации (email + webhook/Telegram).

## Роли (RBAC)
- Оператор — ввод и просмотр своих простоев.
- Специалист по простоям — конструктор кейсов, классификация, RCA.
- Руководитель ИТ — дашборды, эскалации, подтверждение.
- Руководство предприятия — read-only отчёты и KPI.
- Администратор — справочники, ставки, контракты SLA, пользователи.

## Бизнес-правила (кратко)
- `duration_min = ended_at - started_at`
- `losses = duration_hours × loss_rate(unit) + unproduced_tons × ton_margin` (ставки из справочников)
- `availability = (planned_time - downtime) / planned_time`
- `MTTR = Σ duration / count(incidents)`; `MTBF = operating_time / count(failures)`
- Штраф — только для событий с `fault_side = IT` и статусом `CONFIRMED`/`CLOSED`.
- Ставки, пороги и коэффициенты хранятся в БД с версионированием на дату события.
