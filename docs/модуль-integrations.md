# Модуль: интеграции (Этап 6)

Документ объясняет простыми словами, как портал общается с внешними системами:
источником простоев (внешняя **БД с простоями**) и системой тикетов. Пока — в **мок-режиме**,
без доступа к корпоративной сети.

## Главная идея: mock и live

Один и тот же код работает в двух режимах, переключение — переменной в `.env`:

| Режим | Когда | Что внутри |
|---|---|---|
| `INTEGRATION_MODE=mock` | разработка (сейчас) | встроенные строки-примеры, работает без внешней БД |
| `INTEGRATION_MODE=live` | прод в доменной сети | реальные внешняя БД и система тикетов |

Доменная логика (импорт, расчёты) не знает, какой режим включён, — она работает с общим
интерфейсом адаптера. Поэтому при переносе на прод меняем только `.env`, а не код.

## Роль портала: фильтр, а не сборщик

Портал **не собирает** простои сам. Его задача — **читать** простои из внешней БД (только `SELECT`),
**фильтровать** их по вине ИТ и приводить к удобному для ИТ виду. Что именно значит «удобный вид»,
уточняется с руководителем (question.md, В43).

## Устройство (папка `apps/integrations/`)

| Файл | Что делает |
|---|---|
| `saarc.py` | Источник простоев: `BaseSaarcSource` (портрет) + `MockSaarcSource` + `LiveSaarcSource` (код не переименовываем) |
| `omnitracker.py` | Тикеты: `BaseOmniTracker` + `MockOmniTracker` + `LiveOmniTracker` (`fetch_tickets` — чтение, `create_ticket` — создание тикета) |
| `factory.py` | Выбирает mock/live по `INTEGRATION_MODE` |
| `services.py` | Импорт и синхронизация простоев: сопоставление со справочниками, идемпотентность, отчёт |
| `models.py` | `TicketLink` (связь «простой/кейс ↔ тикет») и `SyncRun` (журнал запусков синхронизации) |
| `views.py`, `urls.py` | Страница «Синхронизация»: «Забрать сейчас», «Закрыть период», список «на проверку» |

## Импорт простоев

Команда:
```bash
python manage.py import_saarc                        # за весь доступный период (мок)
python manage.py import_saarc --since 2026-09-01 --until 2026-10-01
python manage.py import_saarc --create-missing       # создавать недостающие участки/агрегаты
python manage.py import_saarc --update               # обновлять уже загруженные строки
```

Что происходит по шагам:
1. Источник отдаёт строки (в мок-режиме — встроенные, в формате источника: русские колонки).
2. **Оставляем только `СЛУЖБА` = наша ИТ-служба** — это наши простои. Остальные службы отфильтровываются.
3. Сопоставляем со справочниками: `ЦЕХ` → цех, `УЧАСТОК` → участок, `АГГРЕГАТ` → агрегат.
   Если чего-то нет — строку **пропускаем** и пишем причину в отчёт (ключ `--create-missing`
   создаёт недостающее, но не цех: цех — верхний уровень, его заводят вручную в справочнике).
4. **Идемпотентность:** внешний ID = отпечаток строки (хэш начала/конца/цеха/агрегата/ФИО/
   примечания). Повторный импорт не создаёт дублей.
5. Импортированные простои получают статус **«Новый»** и вину **ИТ** — их далее подтверждает
   оператор (в расчёт потерь и SLA попадают только «Подтверждён»/«Закрыт»).

Отчёт в конце — примерно такой:
```
Всего строк из источника: 5
  создано: 3
  уже было (пропущено): 0
  обновлено: 0
  не наша служба (отфильтровано): 1
  не найдено в справочнике (пропущено): 1
Замечания:
  - цех «НЕИЗВЕСТНЫЙ ЦЕХ»: найдено 0 совпадений (нужно ровно одно)
```

## Синхронизация и версии записей (Этап 11.6)

Отличие синхронизации от простого импорта: записи **никогда не удаляются**, а изменения
из источника аккуратно **помечаются** и уходят **«на проверку»** к живому человеку.

```bash
python manage.py sync_saarc                     # окно последние 2 часа (для запуска раз в час)
python manage.py sync_saarc --since 2026-09-01 --until 2026-10-01
python manage.py sync_saarc --create-missing    # создавать недостающие участки/агрегаты
python manage.py sync_saarc --no-notify         # не слать уведомления о новых простоях
```

Что происходит:
1. Источник читается как обычно (только `SELECT`), строки фильтруются по нашей службе.
2. **Устойчивый ключ строки** = хэш `НАЧАЛО + ЦЕХ + УЧАСТОК + АГГРЕГАТ + ФИО`. Он **не меняется**,
   если в источнике поправили конец или примечание, — поэтому запись находится и обновляется,
   а не дублируется.
3. Правила по каждой строке:

| Что в источнике | Что делает портал | Метка | Журнал |
|---|---|---|---|
| новая строка | создаёт простой (статус «Новый») | — | «Импорт из СААРЦ» |
| поправили описание/ФИО | обновляет запись | **Исправлен** | «Правка из источника» |
| поправили время (конец) | обновляет запись | **Скорректирован** | «Правка из источника» |
| строку сняли | **не удаляет**, помечает | **Снят** | «Снято в источнике» |
| ничего не изменилось | ничего | — | — |

   Все изменённые/снятые записи получают флаг **«на проверку»** и попадают в список
   `Синхронизация → На проверку`. После проверки человек жмёт «Подтвердить» — запись уходит
   из списка, а **метка остаётся в истории**.

4. **Закрытые периоды не изменяются** — ни правки, ни снятия, ни новые строки закрытого месяца.

### Страница «Синхронизация» (в портале)

Меню **«Синхронизация»** (`/sync/`) — доступна ролям «Специалист по простоям», «Руководитель ИТ»,
«Администратор»:

- **«Забрать сейчас»** — ручной запуск за последние 7 дней (в любой момент);
- **«Закрыть период»** — закрыть месяц: его простои больше не меняются (см. `ReportingPeriod`);
- **«На проверку»** — список записей, которые источник поправил/снял;
- таблица **запусков синхронизации** (когда, каким способом, сколько создано/исправлено/снято).

### Автосбор по расписанию

Раз в час запускается `sync_saarc` (окно 2 часа — с перекрытием). Пример строки для cron — в
`deploy/crontab.example`. Сам портал расписание не держит: используется стандартный cron сервера.

### Журнал запусков

Каждый запуск (авто или вручную) пишется в `SyncRun` — видно, что и когда подтянулось. Полный
текст отчёта каждого запуска — в админке (**Запуски синхронизации**).

## Тикеты

Тикеты связываются с нашими простоями/кейсами отдельной таблицей `TicketLink`
(один инцидент ↔ много тикетов). В мок-режиме доступны тестовые тикеты.

```bash
python manage.py sync_tickets --list     # показать доступные тикеты
python manage.py sync_tickets            # обновить статусы уже привязанных тикетов
```

> Новые связи автоматически не создаются: правило «какой тикет к какому инциденту»
> ещё согласуется (см. `question.md`, В16). Пока связи заводятся вручную в админке
> (**Связи с тикетами**).

### Отправка мероприятия разбора в OMNITRACKER (Этап 11.7, шаг 6)

На карточке разбора у каждого **мероприятия** есть кнопка «В OMNITRACKER»: выбираем группу
и отправляем. Портал вызывает `create_ticket` адаптера и сохраняет номер тикета и ссылку
у мероприятия (видны на карточке и в истории разбора).

- В разработке (`INTEGRATION_MODE=mock`) тикет не уходит наружу — выдаётся учебный номер
  вида `INC-900001`.
- На проде (`INTEGRATION_MODE=live`) нужны `OMNITRACKER_BASE_URL`/`USER`/`PASSWORD`.
- **Дополнительная функция:** если OMNITRACKER недоступен, портал покажет понятную ошибку,
  а сам разбор продолжит работать.
- Список групп — из `OMNITRACKER_GROUPS` (`.env`, через запятую).

## Источник: только чтение

Реальный источник (`LiveSaarcSource`) делает **только `SELECT`** — ничего не меняет.
Запрос конструируется по таблице из `SAARC_DOWNTIME_TABLE` (уточняется после выдачи
доступа, В17, В46). Драйвер `python-oracledb` подключается **лениво** — в мок-режиме он не нужен.
СУБД источника пока уточняется (В46): сейчас код рассчитан на Oracle, при другой СУБД меняется
только `LiveSaarcSource`.

## Зависимости

- Основные — в `requirements.txt` (нужны всегда).
- Только для live-режима — в `requirements-live.txt` (`python-oracledb`, `requests`).
  На проде: `pip install -r requirements-live.txt`.

## Переменные `.env`

```
INTEGRATION_MODE=mock            # mock | live
SAARC_USER=                      # live
SAARC_PASSWORD=                  # live
SAARC_DSN=                       # live
SAARC_DOWNTIME_TABLE=DOWNTIMES   # имя таблицы/представления с простоями
OMNITRACKER_BASE_URL=            # live
OMNITRACKER_USER=                # live
OMNITRACKER_PASSWORD=            # live
```
