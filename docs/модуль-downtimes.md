# Модуль: простои и кейсы (этапы 3–4, 11.7)

Документ объясняет простыми словами, как устроен учёт простоев и объединение дублей в кейсы.
Справочники — в `модуль-catalog.md`. Расчёт потерь и SLA — этап 5.

Зачем нужны кейсы: в источнике один сбой часто записан несколько раз (разные агрегаты и люди).
Если считать каждую запись, потери задваиваются. **Кейс** — это «настоящий» инцидент,
в который мы собираем такие дубли.

## Таблицы

### Простой (`DowntimeEvent`)
Одно событие: когда, где, по какой причине и в каком состоянии.

| Группа | Поле | Смысл |
|---|---|---|
| Время | `started_at` | Начало простоя |
| | `ended_at` | Окончание (пусто = простой ещё идёт) |
| | `duration_min` | Длительность в минутах |
| Место | `workshop` | Цех (**обязательно**) |
| | `section` | Участок (необязательно) |
| | `unit` | Агрегат (необязательно) |
| Вина | `service` | Служба (по умолчанию — наша ИТ-служба) |
| | `fault_side` | Вина ИТ / Другая служба / Не определена |
| | `fault_category` | Категория вины (Сеть, ПО, …) |
| | `fault_subcategory` | Подкатегория вины |
| Описание | `note` | Текст: что случилось |
| | `recorded_by_name` | Кто зафиксировал (ФИО) |
| Состояние | `status` | Новый / Подтверждён / Закрыт / Отменён |
| Источник | `source` | Вручную / внешняя БД / Файл |
| | `external_id` | ID из внешней системы (для повторного импорта) |
| | `raw` | Исходная строка «как пришла» (JSON) |
| Синхронизация | `source_key` | Устойчивый ключ строки-источника (сопоставление при повторной синхронизации) |
| | `sync_mark` | Метка: Исправлен / Скорректирован / Снят (записи **никогда не удаляем**) |
| | `needs_review` | «На проверку» — источник изменил или снял запись |
| | `synced_at` | Когда последний раз видели запись в источнике |
| Объединение | `case` | Кейс, в который входит простой (пусто = сам по себе) |
| Аудит | `created_by`, `updated_by` | Кто завёл/изменил |
| | `created_at`, `updated_at` | Когда завели/изменили |

**Предприятие отдельно не хранится** — его больше нет в структуре; верхний уровень — цех.

### Кейс (`DowntimeCase`)
«Настоящий» инцидент, собранный из дублей.

| Группа | Поле | Смысл |
|---|---|---|
| | `number` | Номер вида `К-2026-0001` (присваивается сам) |
| | `title` | Короткое название |
| | `status` | Открыт / Подтверждён / Закрыт / Отменён |
| Вина | `fault_side`, `fault_category`, `fault_subcategory` | Официальная классификация (берётся из событий, но можно править) |
| Период | `started_at`, `ended_at`, `duration_min` | Считаются из входящих событий (только чтение) |
| | `note` | Описание |
| Аудит | `created_by`, `updated_by`, `created_at`, `updated_at` | |

### Журналы (`DowntimeEventLog`, `DowntimeCaseLog`)
Аудит: кто, когда и что менял. Ведётся **автоматически** через `services.py`
(`save_with_audit`, `save_case_with_audit`) — одним правилом и для админки, и для импорта.

### Закрытый период (`ReportingPeriod`)
Месяц, закрытый для изменений (кнопка **«Закрыть период»** на странице «Синхронизация»).
Закрытые периоды **не изменяются** при синхронизации: ни правки, ни снятия, ни новые строки
закрытого месяца. Дашборды при этом строятся сразу — период не влияет на живые отчёты.

## Как считается длительность

- **Простоя** — хранится в `duration_min`, но пересчитывается автоматически при каждом
  сохранении из начала/конца. В отчётах быстро, при этом всегда верно.
- **Кейса** — **объединением интервалов**: перекрывающиеся куски считаются один раз,
  разнесённые по времени — складываются. Это и есть защита от двойного счёта.

Пример (сбой одной ИТ-системы, 5 записей):

| Способ | Результат |
|---|---|
| Простая сумма записей | 57 мин ❌ |
| **Объединение интервалов** | **23 мин** ✅ |

## Главное правило
**Простой, попавший в кейс, отдельно не считается.** В отчётах берётся либо кейс целиком,
либо одиночный простой — но не оба.

## Как объединять
Админка → **Простои**:
1. Выделите записи галочками → действие **«Объединить выбранные в один кейс»**.
2. Либо кнопка **«Возможные дубли»** сверху: портал сам найдёт похожие записи
   (одинаковое примечание, один цех, начало в пределах 2 часов) и предложит
   объединить группу одной кнопкой.
3. Классификация вины для кейса берётся из событий; название — из примечания.

Карточка кейса показывает его состав и итоговую длительность. Привязка/отвязка изменений
пишется в журнал. Команда `recalc_cases` пересчитывает все кейсы разом.

> Примечание: при удалении кейса его события автоматически «отцепляются» (остаются, но без кейса).

## Проверки целостности (на уровне БД)
- Окончание не раньше начала (`downtime_ended_after_started`).
- Внешний ID уникален в пределах источника (`uniq_source_external_id`) — защита от дублей при импорте.

## Как работать
Админка: http://127.0.0.1:8000/admin/
- **Простои** — фильтры по статусу, вине, источнику, цеху, категории и кейсу;
  поиск; навигация по датам; история изменений на карточке; кнопка «Возможные дубли».
- **Кейсы** — список с составом и длительностью, фильтры, история.
- **Журнал простоев / Журнал кейсов** — отдельные страницы только для чтения.

## Раздел «Простои» в портале (этап 11.7)

Раньше простой был виден только в админке Django. Теперь у него есть обычная страница портала:

- **Список «Простои»** (`/downtimes/`, ссылка в шапке) — фильтры: период, цех, категория вины,
  вина, статус, источник, «на проверку», поиск по примечанию и ФИО. По 50 записей на страницу.
- **Карточка простоя** (`/downtimes/<номер>/`) — все детали: где и когда, классификация вины,
  описание, данные источника и синхронизации, связанные тикеты, история изменений.

Просмотр доступен **любому вошедшему сотруднику** (как дашборд и отчёты). Карточка — «дверь»
к **разбору простоя** (тот же этап 11.7, следующий шаг — см. `docs/план.md`).

Из списка можно отметить один или несколько простоев и **создать разбор** — отдельный модуль,
см. [`модуль-reviews.md`](модуль-reviews.md).

## Демо-данные
```bash
./.venv/bin/python manage.py seed_catalog       # сначала справочники
./.venv/bin/python manage.py seed_downtimes     # затем простои
```
Создаёт 6 простоев. Пять — один сбой одной ИТ-системы, размноженный по агрегатам и людям
(их и объединяем в кейс). Одна — «не наша вина» (отключение электроэнергии).
Команда идемпотентна (опознаёт по внешнему ID).
