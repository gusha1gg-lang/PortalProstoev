# Модуль: простои (Этап 3)

Документ объясняет простыми словами, как устроен учёт простоев. Справочники — в
`модуль-catalog.md`. Объединение простоев в «кейсы» — этап 4, расчёт потерь и SLA — этап 5.

## Две таблицы

### Простой (`DowntimeEvent`)
Одно событие: когда, где, по какой причине и в каком состоянии.

| Группа | Поле | Смысл |
|---|---|---|
| Время | `started_at` | Начало простоя |
| | `ended_at` | Окончание (пусто = простой ещё идёт) |
| | `duration_min` | Длительность в минутах |
| Место | `workshop` | Цех (**обязательно**) |
| | `section` | Участок (необязательно) |
| | `unit` | Агрегат (необязательно) |
| Вина | `service` | Служба (по умолчанию «ДИТ») |
| | `fault_side` | Вина ИТ / Другая служба / Не определена |
| | `fault_category` | Категория вины (Сеть, ПО, …) |
| | `fault_subcategory` | Подкатегория вины |
| Описание | `note` | Текст: что случилось |
| | `recorded_by_name` | Кто зафиксировал (ФИО) |
| Состояние | `status` | Новый / Подтверждён / Закрыт / Отменён |
| Источник | `source` | Вручную / Oracle / Файл |
| | `external_id` | ID из внешней системы (для повторного импорта) |
| | `raw` | Исходная строка «как пришла» (JSON) |
| Аудит | `created_by`, `updated_by` | Кто завёл/изменил |
| | `created_at`, `updated_at` | Когда завели/изменили |

**Предприятие отдельно не хранится** — оно вычисляется через цех (цех → предприятие).
Так нет дублирования: поменяли цех — «переехало» и предприятие.

### Как считается длительность
Длительность **хранится** в поле `duration_min`, но **заполняется автоматически** при каждом
сохранении из начала и конца. То есть в отчётах она быстрая, и при этом всегда верная.
Если окончание не заполнено (простой идёт) — длительность 0.

### Журнал изменений (`DowntimeEventLog`)
Аудит: кто, когда и что менял в простоях.

| Поле | Смысл |
|---|---|
| `event` | Ссылка на простой |
| `user` | Кто (пусто = система, например импорт) |
| `action` | Создание / Изменение / Смена статуса / Объединение |
| `changes` | JSON «что было → что стало» |
| `comment` | Комментарий (необязательно) |
| `created_at` | Когда |

Журнал ведётся **автоматически**: логика в `services.py` (`save_with_audit`). Через неё
пишут и админка, и (позже) импорт из Oracle. Поэтому в одном месте правило аудита.

## Проверки целостности (на уровне БД)
- Окончание не может быть раньше начала (`downtime_ended_after_started`).
- Внешний ID уникален в пределах источника (`uniq_source_external_id`) — защита от дублей при импорте.

## Как работать
Админка: http://127.0.0.1:8000/admin/ → раздел **Простои**.
- Список с фильтрами по статусу, вине, источнику, предприятию, цеху и категории.
- Поиск по примечанию, ФИО, внешнему ID, цеху, агрегату.
- Навигация по датам (сверху).
- На карточке простоя внизу — **история изменений** (только чтение).

## Демо-данные
```bash
./.venv/bin/python manage.py seed_catalog       # сначала справочники
./.venv/bin/python manage.py seed_downtimes     # затем простои
```
Создаёт 6 простоев по данным выгрузки. Пять из них — один и тот же сбой
(«система ДМАП»), размноженный по агрегатам и людям: на этапе 4 покажем объединение
в один кейс, чтобы потери не задваивались. Одна запись — «не наша вина» (отключение
электроэнергии). Команда идемпотентна (опознаёт по внешнему ID).
