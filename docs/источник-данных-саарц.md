# Источник данных: база СААРЦ

Описание того, откуда портал берёт простои. Нужно для Этапа 6 (интеграция), когда появится доступ
к базе СААРЦ. Данные собраны из скриншота внутреннего сайта и выгрузки Excel.

## Что такое СААРЦ

**СААРЦ** — «Система автоматизированного анализа работы цеха», собственная разработка ОМК.
Она собирает и анализирует данные с производственного оборудования в реальном времени (например,
сигнал «начало резки трубы», «замедленное охлаждение»), помогает оценивать эффективность процессов,
выявлять узкие места и оптимизировать работу цехов. Автоматическую фиксацию простоев в неё добавили
позже — сначала её не было.

## Роль портала: фильтр, а не сборщик

Портал **не собирает** простои сам. Он:
1. **читает** простои из базы СААРЦ (только `SELECT`, ничего не меняем);
2. **фильтрует** их — оставляет записи по вине ИТ (служба ДИТ);
3. **приводит к удобному для ИТ виду** — объединяет дубли в один кейс, классифицирует вину,
   считает потери и SLA, показывает на дашборде и в отчётах.

## Где живут данные
- Внутренний сайт «Количество простоев» (разделы: Отчётность, Ввод данных, Документы) — витрина
  над базой СААРЦ.
- Данные берутся из **базы СААРЦ** (доступ пока не выдан).
- Наша часть данных — записи службы **ДИТ** (прежнее название компании — ОМК-ИТ).

## Фильтры на сайте
- Начало периода, Конец периода, Задать время
- **Служба** — ответственная служба (наша = ДИТ)
- **Цех** — выпадающий список вида «Предприятие — Объект» («АО ВМЗ — КЦ», «МК ОМК-Экометалл — Киржач» и т.д.)

## Структура таблицы простоев (колонки)

| Колонка | Пример | Смысл |
|---|---|---|
| НАЧАЛО | 2026-10-10 15:01:25 | Начало простоя |
| КОНЕЦ | 2026-10-10 15:24:47 | Окончание |
| ДЛИТЕЛЬНОСТЬ | 0ч.23мин. | Текстовая длительность (считаем сами из начала/конца) |
| ПРИЧИНА | *(пусто)* | Категория причины (требует уточнения) |
| ПРИМЕЧАНИЕ | «Не работает система ДМАП» | Текст, что произошло |
| АГГРЕГАТ | «Участок гидропресса №2 — П9046-2» | Конкретный агрегат |
| УЧАСТОК | «Участок ремонта и гидроиспытаний 1020» | Участок |
| ФИО | «Кондрушин А.М.» | Кто зафиксировал |
| СЛУЖБА | ДИТ | Ответственная служба |
| ЦЕХ | ТЭСЦ-4 | Цех |

## Иерархия (важно)
Реальная структура: **Предприятие → Цех → Участок → Агрегат**.
В портале так же: Предприятие = Enterprise, Цех = Workshop, Участок = Section, Агрегат = Unit.

## Ключевой вывод для запроса
Наши простои = строки, где **`СЛУЖБА = ДИТ`**. Запрос отбирает записи по службе ДИТ за период.
Только чтение (`SELECT`), ничего не меняем.

## Важное наблюдение: дубли и «конструктор»
Один и тот же сбой порождает много записей. Пример (10.10.2026, система ДМАП):
одна остановка в 15:05–15:20 записана дважды (Орлов, Аникин), в 15:09 — дважды, в 15:10 — дважды и т.д.
Это один инцидент, размноженный по агрегатам и людям.
**Вывод:** функция объединения простоев в один кейс (Этап 4) обязательна, иначе потери будут задвоены.

## Формат данных
- Даты/время: `2026-10-10 15:01:25`.
- Длительность: текст вида `0ч.23мин.` — считаем из НАЧАЛО/КОНЕЦ.
- Пример проблемного ПО: **система ДМАП** (прикладное ПО / АСУ).
