# Модуль: справочники и роли (Этап 2)

Документ объясняет структуру данных простыми словами. Здесь только справочники —
производственная структура, категории вины ИТ и ставки потерь. Сами простои будут в модуле `downtimes`.

Названия уровней соответствуют реальным терминам предприятия:
**Цех → Участок → Агрегат** (верхний уровень — цех; уровень «Предприятие» убран полностью,
см. `docs/план.md`, Этап 11.6).

## Таблицы (модели)

### Производственная структура
```
Цех (Workshop)                — верхний уровень, название уникально везде
 └─ Участок (Section)         — название уникально в пределах цеха
     └─ Агрегат (Unit)        — название уникально в пределах участка
```
Агрегат может быть **общецеховым** — без участка, тогда он крепится прямо к цеху
(название уникально в пределах цеха). См. `question.md`, В1.

Опознаём записи **по названию** (в источнике кодов нет). Поле «Код» — необязательное,
если где-то понадобится короткий код.

| Таблица | Поля | Смысл |
|---|---|---|
| Цех | название, код (необяз.), активен | Верхний уровень (например, «ТЭСЦ-4») |
| Участок | цех, название, код (необяз.), активен | Например, «Участок отделки» |
| Агрегат | цех, участок (необяз.), название, код (необяз.), критичность, активен | Например, «Площадка окончательной приёмки». Без участка — общецеховой агрегат. Критичность: особо важный / высокая / средняя / низкая |

### Производственная структура в портале
Цеха, участки и агрегаты правятся **прямо в портале** — страница **«Структура»**
(`/catalog/structure/`, ссылка в верхнем меню). Это ручное ведение (по `question.md`, В9);
импорт справочников из источника добавим, когда будет доступ к боевой БД.

Как устроено (простыми словами):

- **список цехов** — добавить цех, увидеть число участков и агрегатов, скрыть/вернуть;
- **страница цеха** — переименовать цех, добавить участок, скрыть/вернуть участок;
  отдельно — **общецеховые агрегаты** (без участка): добавить, переименовать,
  сменить критичность;
- **страница участка** — переименовать участок и добавить к нему агрегаты;
  агрегаты правятся прямо в списке: название, критичность, скрыть/вернуть.

Название агрегата уникально в пределах участка (а у общецехового — в пределах цеха),
цех агрегата выводится из участка автоматически. Записи **не удаляются**, только
скрываются и возвращаются — то же правило, что и для классификации.

### Вина ИТ
```
Категория вины ИТ (ItFaultCategory)
 └─ Причина / подкатегория (ItFaultSubcategory)
```
Реальная классификация (2 уровня, из файла руководителя — `question.md`, В3):
**АРМ, Инфраструктура, ЦИС, КИС, «Не наша ИТ-служба»**. У каждой категории — свой список
причин (подкатегорий). Пример: категория «КИС», причина «Программный сбой».

Классификацию ведём сами: категории и причины можно добавлять и править **прямо в портале** —
страница **«Классификация»** (`/catalog/`, ссылка в верхнем меню). Правка через админку тоже
осталась (см. ниже).

**Как это работает (простыми словами).** Есть список **категорий** (АРМ, Инфраструктура, ЦИС,
КИС, «Не наша ИТ-служба»). Внутри каждой — её **причины**. На странице «Классификация»:

- **добавить категорию** — код (латиницей, короткий), название, описание;
- **правка категории** — открыть «Открыть и править»: переименовать, сменить описание,
  показать/скрыть;
- **причины категории** — переименовать каждую, добавить новую (код вида `АРМ-01`
  подставляется сам), показать/скрыть.

Записи **не удаляются**: на категорию/причину ссылаются исторические простои. Ненужное
**скрывается** (`активна = нет`) и при желании возвращается кнопкой «Вернуть». Это тот же
принцип, что и в синхронизации (`docs/модуль-integrations.md`). Тот же приём применили к
старой учебной классификации — она скрыта, но осталась в базе.

**Кто может править:** специалист по простоям, руководитель ИТ, администратор — те же роли,
что и у синхронизации.

### Ставки потерь (LossRate)
Привязаны к участку и **версионируются по датам** (`valid_from`, `valid_to`).
Для конкретного простоя берётся ставка, действовавшая на дату этого простоя.
Поля: потери за час (₽), период действия, примечание.
Есть проверка на уровне БД: дата окончания не раньше даты начала.

## Роли
Роли — это группы Django (создаются миграцией `accounts.0001_create_roles`):

- Оператор
- Специалист по простоям
- Руководитель ИТ
- Руководство предприятия
- Администратор

Имена ролей лежат в `apps/accounts/roles.py`. Там же — заготовка маппинга групп AD → роли
(заполним на этапе 9, когда подключим SSO).

## Как вести справочники
Через **портал**: страница «Классификация» (`/catalog/`) — категории и причины вины ИТ;
страница **«Структура»** (`/catalog/structure/`) — цеха, участки и агрегаты.
Через **админку** Django: http://127.0.0.1:8000/admin/ — раздел «Справочники».
В админке можно добавлять цеха (с участками прямо внутри формы), агрегаты, категории вины
(с подкатегориями внутри) и ставки. Программировать для этого не нужно.

## Данные справочников
```bash
./.venv/bin/python manage.py seed_catalog
```
Заполняет перечень цехов по данным заказчика, а также **5 категорий вины ИТ**
(с причинами — 2 уровня, реальный список, см. `question.md`, В3) и 4 демо-ставки.
Старая (учебная) классификация не удаляется, а помечается неактивной. Для примера детально
наполнен один цех (4 участка, 5 агрегатов) — по данным выгрузки Excel. Команда идемпотентна —
повторный запуск дублей не создаёт.

Полный список цехов ведётся отдельно (во внутреннем документе).
