# Источник данных: БД с простоями

Описание того, откуда портал берёт простои. Нужно для Этапа 6 (интеграция), когда появится доступ
к базе. Данные собраны из скриншота внутреннего сайта и выгрузки Excel.

> **Обезличено.** Названия компании, заводов и систем заменены нейтральными терминами
> («компания», «завод», «ИТ-служба», «БД с простоями»). Полный список предприятий и цехов
> ведётся отдельно, во внутреннем документе, и в публичный репозиторий не выкладывается.

## Роль портала: фильтр, а не сборщик

Портал **не собирает** простои сам. Он:
1. **читает** простои из БД с простоями (только `SELECT`, ничего не меняем);
2. **фильтрует** их — оставляет записи по вине нашей ИТ-службы;
3. **приводит к удобному для ИТ виду** — объединяет дубли в один кейс, классифицирует вину,
   считает потери и SLA, показывает на дашборде и в отчётах.

## Где живут данные
- Внутренний сайт «Количество простоев» (разделы: Отчётность, Ввод данных, Документы) — витрина
  над базой простоев.
- Данные берутся из **БД с простоями** (доступ пока не выдан).
- Наша часть данных — записи нашей ИТ-службы.

## Фильтры на сайте
- Начало периода, Конец периода, Задать время
- **Служба** — ответственная служба (наша = ИТ-служба)
- **Цех** — выпадающий список вида «Предприятие — Объект»

## Структура таблицы простоев (колонки)

| Колонка | Пример | Смысл |
|---|---|---|
| НАЧАЛО | 2026-10-10 15:01:25 | Начало простоя |
| КОНЕЦ | 2026-10-10 15:24:47 | Окончание |
| ДЛИТЕЛЬНОСТЬ | 0ч.23мин. | Текстовая длительность (считаем сами из начала/конца) |
| ПРИЧИНА | *(пусто)* | Категория причины (требует уточнения) |
| ПРИМЕЧАНИЕ | «Не работает система …» | Текст, что произошло |
| АГГРЕГАТ | «Участок гидропресса №2 — П9046-2» | Конкретный агрегат |
| УЧАСТОК | «Участок ремонта и гидроиспытаний 1020» | Участок |
| ФИО | «Иванов И.И.» | Кто зафиксировал |
| СЛУЖБА | *(наша ИТ-служба)* | Ответственная служба |
| ЦЕХ | *(название цеха)* | Цех |

## Иерархия (важно)
В источнике структура идёт от предприятия: Предприятие → Цех → Участок → Агрегат.
**В портале уровень «Предприятие» убран** (решение руководителя, Этап 11.6) —
верхний уровень это **Цех**: Цех = Workshop, Участок = Section, Агрегат = Unit.

## Ключевой вывод для запроса
Наши простои = строки, где **`СЛУЖБА` = наша ИТ-служба**. Запрос отбирает записи по нашей службе
за период. Только чтение (`SELECT`), ничего не меняем.

## Важное наблюдение: дубли и «конструктор»
Один и тот же сбой порождает много записей: одна и та же остановка записывается по нескольким
агрегатам и людям. Это один инцидент, размноженный по агрегатам и людям.
**Вывод:** функция объединения простоев в один кейс (Этап 4) обязательна, иначе потери будут задвоены.

## Формат данных
- Даты/время: `2026-10-10 15:01:25`.
- Длительность: текст вида `0ч.23мин.` — считаем из НАЧАЛО/КОНЕЦ.
- Проблемное ПО бывает прикладным (АСУ/ПО цеха).

## Список объектов
Полный список цехов группы ведётся отдельно, во внутреннем документе
(в публичный репозиторий не выкладывается). В портале цеха (модель Workshop) —
верхний уровень, заполняются командой `seed_catalog`. Справочники опознаются по названию
(кодов в источнике нет).
