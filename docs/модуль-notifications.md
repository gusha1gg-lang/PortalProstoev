# Модуль: уведомления и эскалации (Этап 8)

Документ объясняет простыми словами, как портал рассылает уведомления.
Сейчас канал **один — электронная почта**. Другие каналы (например, Telegram) добавятся
позже, не переделывая правила.

## Главная идея

- **Правило** отвечает на вопросы: *по какому событию*, *кому* и *что написать*.
  Правила и получатели задаются в админке (раздел «Уведомления»).
- **Канал** — способ доставки. Сейчас только email.
- **Журнал** хранит, что уже отправлено, чтобы **не слать одно и то же дважды**.

## События

| Событие | Когда срабатывает |
|---|---|
| Новый инцидент | Простой по вине ИТ создан или импортирован |
| Предупреждение SLA | Простои приблизились к лимиту по договору (по умолчанию 80%) |
| Эскалация SLA | Лимит по договору превышен |
| Периодическая сводка | По расписанию (ежедневно утром) |

## Почта: разработка и прод

Письма отправляются стандартным механизмом Django, поэтому переключение «заглушка → прод»
делается настройкой, без правки кода:

| Среда | Backend | Куда уходят письма |
|---|---|---|
| Разработка | `console` | **Печатаются в консоль сервера** (никуда не уходят) |
| Прод | `smtp` | Реальный почтовый сервер, реквизиты из `.env` |

Реквизиты SMTP (сервер, порт, шифрование, учётка) уточняются у коллег из ПИ-ПС —
см. `question.md`, В22–В24. Для проверки почты есть команда `notify_test`.

## Команды (и расписание)

```bash
python manage.py check_escalations        # проверка лимитов SLA (cron каждые 5–10 мин)
python manage.py send_digest              # сводка (cron ежедневно утром)
python manage.py notify_test --to a@b.ru  # проверочное письмо
```

Пример записи в cron на проде:

```cron
*/10 * * * * cd /opt/portal && ./.venv/bin/python manage.py check_escalations >> /var/log/portal-notify.log 2>&1
0 8   * * * cd /opt/portal && ./.venv/bin/python manage.py send_digest      >> /var/log/portal-notify.log 2>&1
```

Обе команды можно запускать с `--date "ГГГГ-ММ-ДДThh:mm"` — удобно для проверки.

## Защита от повторов

У каждой успешной отправки есть ключ уникальности (`dedup_key`). Если то же письмо
попробует уйти снова (повторный запуск команды), оно не отправится.
Если отправка **не удалась** — ключ не сохраняется, поэтому при следующем запуске
письмо попробует уйти ещё раз.

## Где смотреть

- **Страница «Уведомления»** (`/notifications/`) — журнал отправок: что/кому/когда.
  В разработке тут видно письма, которые ушли «в консоль».
- **Админка** → «Правила уведомлений» — настройка правил и получателей.

## Устройство (папка `apps/notifications/`)

| Файл | Что делает |
|---|---|
| `models.py` | `NotificationRule` (правило), `NotificationRecipient` (получатель), `NotificationLog` (журнал) |
| `channels.py` | Каналы доставки: `EmailChannel` (заготовка под будущие каналы) |
| `services.py` | Логика: применение правил, защита от повторов, эскалации, сводка |
| `views.py` / `templates/notifications/log.html` | Журнал отправок |
| `management/commands/` | `check_escalations`, `send_digest`, `notify_test`, `seed_notifications` |
| `tests.py` | Тесты отправки, повторов, эскалаций и сводки |

## Связь с другими модулями

- Формулы SLA (лимит, штраф) уведомления берут из модуля `sla` — цифры те же, что на дашборде.
- Сводка берёт готовые показатели из модуля `reports`.
- Импорт из Oracle (`import_oracle`) уведомляет о каждом новом простое; для массового
  исторического импорта есть ключ `--no-notify`.
